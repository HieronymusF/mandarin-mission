# ADR 0002：采用代码优先的 shadcn UI 流程

- 状态：Accepted
- 日期：2026-07-18
- 影响范围：Flutter 移动端、前端开发流程、UI 验收与 AI 协作

## 背景

原流程要求每个用户可见改动先在 Figma 画原型、确认节点链接，再由代理还原为 Flutter。对一人开发且大量依赖 AI 的项目，这产生了三次表达同一信息的成本：需求描述、Figma 原型和 Flutter 代码；原型到代码的上下文也显著增加 Token 消耗。

项目当前只有 Flutter 客户端。`ui.shadcn.com` 官方组件是 React 代码，不能直接运行在 Flutter，但它的语义化主题、组合式组件和开放代码理念适合作为 UI 基线。Flutter 生态已有兼容当前工具链的移植实现。

## 决策

1. 前端改为代码优先：需求和状态明确后，直接从组件库组合 Flutter 页面。
2. 视觉原则与组件目录参考官方 [shadcn/ui](https://ui.shadcn.com/docs)。
3. 实际运行依赖固定为 MIT 许可的 `shadcn_ui: 0.55.0`，通过 `ShadApp.custom` 与现有 Material、Riverpod 和 go_router 共存。
4. 项目主题令牌、组件白名单和页面状态写入 `docs/design-system.md`，可执行值放在 `app_theme.dart`。
5. Figma 改为按需工具，不再作为前端开始编码、提交 PR 或交付的强制门槛。
6. UI 验收改为：自动测试 + 关键状态截图 + 常见设备/大字体检查；复杂交互再补视觉稿或可交互原型。

## 结果

正面影响：

- 减少重复原型和还原工作，降低独立开发与 AI Token 成本；
- 组件、状态和主题在代码中有单一来源；
- 现有 Flutter 页面可以渐进迁移，不需要重写路由或数据层；
- 代理不因缺少 Figma 工具而被阻塞。

代价与风险：

- `shadcn_ui` 是社区维护的 `0.x` 包，升级可能包含破坏性变化；
- 引入额外传递依赖和包体积；
- 没有逐页原型时，必须依靠严格令牌、组件白名单和截图回归避免视觉漂移；
- React 官方组件与 Flutter 移植版并非一一对应，缺失组件需要组合或本地实现。

缓解措施：

- 固定精确版本，升级单独成 PR；
- Material 只作为平台外壳和兼容层，业务 UI 优先使用已确认的 shadcn 原语；
- 不为缺失组件立即引入第二套 UI 库；
- 关键页面保留 Widget/集成测试，并逐步增加 Golden 与真实设备截图。

## 备选方案

- 继续 Figma-first：视觉评审明确，但重复工作和 Token 成本最高。
- 只用原生 Material 3：依赖最少，但组件默认风格和跨页面约束需要项目自行维护。
- 新增 React Web 前端：与移动产品目标不符，并会形成第二套客户端。

## 回滚

业务状态、路由、Repository 与 shadcn 组件保持分层。若移植包出现不可接受的维护或体积问题，可保留相同语义令牌，把 `ShadButton`、`ShadCard`、`ShadBadge` 和 `ShadProgress` 逐步替换为项目内 Material 组件，不影响数据层和学习规则。
